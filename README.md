# Agentic Codemod Tool

A CLI that takes a plain-English instruction and a target file, and produces a reviewable diff: `codemod run "rename the color prop to tone on MyButton" --path src/`. Deterministic AST transforms handle the instructions that match a known shape (Tier 1); an LLM handles everything else (Tier 2). Both tiers go through the same safety rail before a diff is ever shown — the change is written to the real file on disk, type-checked (and test-run, if a test command is given), then always reverted. Nothing survives to disk without an explicit `--apply --yes`.

This generalizes work I've done at Delivery Hero maintaining large-scale internal refactors by hand (prop renames, import path migrations, class-to-hooks conversions across dozens of call sites). That work was always "I know exactly what needs to change, I just have to do it everywhere correctly" — this tool is that instinct made into something that can also take an instruction it wasn't specifically coded to handle, safely, because the safety rail doesn't care which tier produced the diff.

## Eval numbers (up front, not buried)

Measured against `llama3.2:3b` running locally via Ollama, 24 cases (`evals/cases.ts`: 12 Tier 1, 12 Tier 2, 8 adversarial — designed to correctly fail). Numbers are the mean of 3 consecutive live runs, not a single sample — see below for why:

- **Tier 1 (canned transforms) success rate: 100%** — deterministic, no LLM call, reproduces exactly across 5 separate live runs during development.
- **Tier 2 (LLM-in-the-loop) success rate: 86.1%**
- **Correct-refusal rate (adversarial subset): 85.2%**

Full breakdown in `evals/results.md`, regenerated by `pnpm eval`.

**Why averaged, not a single run:** Tier 2's success and correct-refusal rates swing 25-33 points run-to-run on the exact same 24 cases with no code change — genuine `llama3.2:3b` sampling noise, confirmed by re-running the identical eval 5 times during development (75-100% and 67-100% respectively). A baseline written from one run can land anywhere in that range, including its ceiling — an early single-run 100%/100% baseline turned out to be exactly that, an outlier, and would have made every subsequent honest run look like a regression. Both `pnpm eval` (writes the baseline) and `pnpm eval:check` (CI gate) now run the suite 3 times and report the mean.

## Architecture

```
plain-English instruction
      │
      ▼
instruction-parser.ts ── matches a known phrasing? ──► Tier 1: canned AST transform (ts-morph)
      │                                                      rename-identifier, rename-import-path,
      │ no match                                             rename-jsx-prop, extract-magic-literal,
      ▼                                                       convert-class-to-function-component
Tier 2: LLM generates full file content
(Ollama default / Anthropic optional)
      │
      ▼
validateChange (shared by both tiers)
  write proposed content over the real file on disk
  type-check via the nearest real tsconfig.json (ts-morph)
  run test command, if given
  ALWAYS revert the file in a finally block
      │
      ├─ passes ──► shown as a diff (dry-run) or written with --apply --yes
      ├─ Tier 2 fails once ──► retry with the failure fed back to the model (one retry, then give up)
      └─ fails ──► reported as unsafe / no-safe-transform, nothing ever touches disk
```

## Design decisions

**Two tiers, one safety rail.** Canned transforms (Tier 1) exist because for a known shape of instruction — rename this, extract that — an AST transform is exact and free. Everything else goes to the LLM (Tier 2). The distinction that actually matters for trust isn't which tier produced a diff, it's that `validateChange` gates both identically: write the real file, type-check it against its real `tsconfig.json`, optionally run its real test command, always revert. A canned transform gets no special trust for being canned — `t1-05`/`t1-09`'s JSX cases and `t1-04`'s import-rename case all correctly fail this gate when their precondition doesn't hold.

**Dry-run by default; `--apply` alone still isn't enough.** `--apply` without `--yes` reports what would change and stops. This mirrors the actual risk profile: type-checking proves a diff doesn't break compilation, not that it does what you meant.

**Works with zero API key or cost by default.** `LLM_PROVIDER` defaults to Ollama (`docker-compose.yml`, host port **11436** — Project 1 already claimed 11435, and this machine's native Ollama install already held 11434). Anthropic is available via `LLM_PROVIDER=anthropic` with `ANTHROPIC_API_KEY` set; not yet used here since this eval's Ollama numbers were sufficient to validate the design — an Anthropic baseline is a pending, optional addition, same status as Project 1's.

## Real limitations found while building this (not hidden)

- **The safety rail verifies the output, not fidelity to the instruction.** This is the single most important limitation, and the eval surfaced it directly, not just in theory: asked to "make this function return `someUndeclaredGlobalVariableXyz` instead of computing the value," the model sometimes correctly refuses (`Cannot find name`), and sometimes sidesteps the impossible part entirely — for example rewriting the return type to `never` and returning `undefined as never`, which type-checks but does nothing resembling the instruction. `validateChange` has no way to tell those two outcomes apart; it only knows the file it's holding compiles. Tightening this would mean asking the model to also self-report whether it followed the instruction, which is at best another unreliable signal layered on an already-unreliable one — documenting the gap honestly seemed more useful than pretending a heuristic patch closes it.
- **Two real bugs, found by the eval harness, not by writing more unit tests.** A shared regex in `instruction-parser.ts` excluded `/` from its character class, so `rename-import-path` never matched any real file path — both a success case and a should-be-unsafe case silently fell through to Tier 2 instead of exercising the canned transform at all. And `convertClassToFunctionComponent` dropped the props type entirely (`function Counter(props) {}`, no annotation) — a `noImplicitAny` violation the class's own `extends Component<CounterProps>` heritage clause had the answer to all along. Both were caught because the eval ran real cases against real `tsc`, not because a unit test happened to assert on the exact right string. See `PLAN.md`'s M2.8 entry for the full account.
- **Small local models sometimes "solve" an infeasible ask instead of declining it.** Related to the first point: a 3B model doesn't reliably distinguish "I can't do this" from "let me find something adjacent that works." A larger model (or Anthropic's) would likely do better here — untested, since that baseline hasn't been recorded yet.
- **`convertClassToFunctionComponent` is deliberately narrow** — single `render()` method, at most one `this.state = {...}` assignment in the constructor, no other lifecycle methods, no multi-key `setState` calls. Anything outside that shape bails out with a specific reason (see the transform's own module comment) rather than guessing at a general rewrite.

## Running it locally

```bash
docker compose up -d                              # starts Ollama on localhost:11436
docker exec <container> ollama pull llama3.2:3b   # one-time, ~2GB

pnpm install
pnpm build
node dist/cli.js run "<instruction>" --path <file-or-dir>              # dry-run
node dist/cli.js run "<instruction>" --path <file-or-dir> --apply --yes # writes to disk
pnpm eval                                          # regenerate evals/results.md (3 live runs)
```
